## Findings

### Critical — production queue mounts the entire task dataset

Route: `#/laundry/production-queue`

At a 1280×800 viewport the live DOM contained:

- 995 task inputs
- 1,321 buttons
- 123,870px document height
- 309 visible `Start` task actions

The interface reports a bounded range (`0–500 of 995`), but the DOM still mounts the full dataset. This defeats the stated scale target, increases layout/paint/keyboard-navigation cost, and makes the floor queue harder to operate as volume grows.

Recommended correction: server pagination or cursor loading plus a virtualized task list. Keep station summaries and urgent/overdue filters server-backed; only mount the visible window and preserve keyboard focus across page/window changes.

### High — order booking mounts the full catalogue in one pass

Route: `#/laundry/new-order`

At the tested tablet viewport the booking surface mounted 216 `Add` controls and 235 images in one DOM pass. The visual catalogue is a strong foundation, but it will become slow and difficult to keyboard-navigate as catalogue size and image weight increase.

Recommended correction: incremental category/service loading or virtualization, stable image dimensions, lazy loading, and a compact result-count/search model. Preserve the visual cards and server-calculated totals.

### High — catalogue command centre has the same scale pattern

Route: `#/laundry/catalogue`

The live surface exposed 216 price rules, 396 buttons and roughly 25,190px of document height. The data is useful, but the matrix should not require one large mounted page.

Recommended correction: paginated/virtualized price matrix, filtered subviews for garments/services/adjustments, and focused drawers for editing rather than rendering every action at once.

### High — rider workflow is not fully real-time or evidence-complete

Route: `#/laundry/dispatch`

The UI truthfully reports safe five-second polling and no SSE/WebSocket feed for this local node. It also explicitly reports that OTP, live GPS, arrival, and proof-of-delivery are not represented until the supporting APIs provide evidence.

This is transparent and safer than fabricating state, but it does not yet satisfy the target of a tightly connected rider-driven operational control centre. Normal rider transitions should arrive through a durable event channel where available, with polling as fallback, and the drawer should show verified OTP/POD evidence when the rider contract supports it.

### High — ordinary order screen still exposes direct delivery mutations

Route: `#/laundry/orders?view=store-orders`

The combined order surface is paginated (`256` matches, six pages), which is good. However, rows still expose direct `Ready`, `In Process`, and `Delivered` actions. This conflicts with the rider-owned normal delivery workflow in the operating mandate, where dashboard actions should focus on assignment and exceptions and manual status changes should be an explicit, reasoned override.

Recommended correction: retain direct actions only where the existing lifecycle rules require them, move exceptional transitions under a permission-gated Manual Override action with reason and audit event, and keep rider-originated events as the normal path.

### Medium — print worksheet drawer is not reliably bounded on narrow layouts

Route: `#/laundry/print-centre`

The All filter correctly loaded 256 worksets and opening a workset correctly preserved the queue behind a live worksheet. At the tested tablet viewport, the worksheet panel was wider than the viewport and its left edge was clipped. At desktop width it behaved as a large right-side panel, but its effective width was still much larger than the intended compact drawer pattern.

Recommended correction: use a viewport-bounded width such as `min(720px, 100vw)` with a stable fixed containing block, verify `right: 0`, prevent horizontal overflow, and add responsive tests for 768px, 1024px, and 1280px widths.

### Medium — customer drawer is functional but oversized at tablet width

Route: `#/laundry/orders?view=customers`

The customer work card is implemented as a true right-side modal drawer over a dimmed page, with Activity/Orders/Ledger tabs and customer totals. At the 652px test viewport it occupied approximately 440px, or 67.5% of the viewport, leaving little context visible behind it.

Recommended correction: keep the current interaction model, but cap tablet width around 50–60% where feasible and fall back to a full-screen sheet only below a deliberate breakpoint. Preserve focus trapping and Escape/close behavior.

### Medium — finance command centre is visually strong but deep

Route: `#/laundry/finance`

The top of the page communicates net revenue, gross profit, EBITDA, cash, receivable and overdue amount clearly, with evidence-backed visual sections. At the tested tablet viewport it contained 23 section headings and approximately 11,146px of document height.

This is not a correctness defect, but it weakens the five-to-ten-second command-centre goal after the first viewport. Recommended correction: keep the top health/attention layer fixed in information architecture, then move detail into tabs or collapsible workspaces (Revenue, Cash, Profitability, Liabilities, Marketplace) with deep links.

## Positive evidence

- Login and workspace boundary worked in the installed build.
- Dashboard loaded live local records and exposed meaningful operational counts.
- Combined orders/customers view is coherent and paginated.
- Customer profile interaction uses the requested side drawer pattern.
- Print Centre loads real demo worksets and opens an in-context worksheet.
- Delivery Operations prioritizes unassigned/exception work and groups rider workload.
- Route Control exposes zones, run progress, and stop state.
- Garment Tracking preserves tag/unit lifecycle language and scanner-oriented flow.
- Quality Claims separates open work, rewash loops, resolved work, and correction actions.
- Finance Setup is intentionally configuration-gated and does not silently claim provider filing or IRP evidence.
- Finance Control Room uses plain-language policy labels with advanced details disclosed progressively.
- Sync Status distinguishes local ledger readiness from absent marketplace connectivity and shows retry/dead-letter/conflict counts.
- No console errors or warnings were observed in the sampled installed-renderer flows.

## External and environment blockers

These are not UI defects and were not fabricated into pass states:

- Marketplace endpoint is not configured in the demo workspace.
- Platform-admin cloud connection is not configured in the demo workspace.
- OTP, live GPS, arrival, and proof-of-delivery require supporting rider APIs/evidence.
- Production Authenticode certificate, trusted update host, real payment/GSP credentials, real hardware verification, and off-device backup provider remain external readiness items.

## Recommended remediation order

1. Virtualize/paginate Production Queue and add a performance regression test at 500–1,000 tasks.
2. Virtualize or incrementally load Order Booking and Catalogue price rules.
3. Fix drawer width/overflow at tablet and desktop breakpoints; add visual regression coverage.
4. Align ordinary delivery mutations with rider-owned transitions and audited manual overrides.
5. Complete rider evidence/event transport when the real rider contract is available.
6. Split deep Finance into focused workspaces without removing the current explainable calculations.
